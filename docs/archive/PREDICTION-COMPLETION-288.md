# Candidate288: a completed server tail can reach a client through Restore

Native287 completed two SPAS pumps and submitted the third full stroke. Server
Update7018 committed7->8->1->2 with5/24 ammunition. ClientA also completed its
tail. ClientB Restore7027 then advanced7/7/8 to2/7/2 from an unchanged idle
snapshot with the same ammunition. The service treated this legitimate forward
prediction correction as a contradiction because clientB had not performed its
own Commit tail. Equipment consequently stayed blocked. The game did not crash;
the diagnostic stopped and drained its hooks.

288 extends the existing M95 forward-completion evidence helper to a configured
held boundary and either client branch. SPAS requires the server's already
completed, fresh, ordered tail. M95 keeps its previously measured clientA-from-
clientB contract. The receiving client must then finish its own neutral idle
Update before voting ready. The snapshot does not invent Commit receipts or
ammunition, issue another physical cycle, or grant Ready by itself. Original
identity, counts, deadlines, callback order, snapshot bytes and configuration
checks remain mandatory. A subsequent native tail replay withdraws only that
client's provisional vote and preserves the submitted physical action.

Six exact native287 callbacks are preserved in SpasForwardRestore287Fixture.h.
The connected service regression fails before the fix. Positive checks cover
both SPAS clients and loaded/empty boundaries; negative checks cover missing or
stale server completion, an open client Update, altered snapshot/ammunition/
owner, invalid phase/timer, pre-release/expired/replayed evidence, and a copy
before the physical stroke. Focused builds, native acceptance and normal builds
must be recorded separately; no headset or whole-campaign approval is implied.
